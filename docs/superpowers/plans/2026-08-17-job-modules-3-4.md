## 2. 模块 3：ProcessGroup

### 2.1 稳定端口

定义一个可替换的进程工厂和终止器协议，调用方显式传入 `argv`、`cwd`、`env` 及 stdio 选项。ProcessGroup 至少提供：

- `start(argv, *, cwd, env, stdin, stdout, stderr) -> ProcessHandle`；
- `poll(handle) -> int | None`、`wait(handle, timeout) -> int`、`pid(handle) -> int`；
- `terminate_tree(handle, timeout) -> TerminationReport`，以及必要的根进程兜底；
- `communicate(handle, timeout) -> (stdout, stderr)` 或等价的句柄级操作；
- `close(handle)`/资源释放语义。

`ProcessHandle` 只暴露所需的 PID、轮询、等待、通信和退出信息，避免后续 Job 重新直接接触 `subprocess.Popen`。默认实现内部仍使用 `Popen`，但 `Popen` 只出现在该模块。

### 2.2 平台规则

- Windows：启动时设置 `CREATE_NEW_PROCESS_GROUP`；终止优先使用 `taskkill /PID <root> /T /F`，使用显式、最小化的环境和超时；命令失败、PID 不存在或根进程已退出均视为幂等终止。
- POSIX：启动时设置 `start_new_session=True`；终止优先 `killpg(root_pid, SIGKILL)`，再对仍存活的根进程调用 `kill()`。
- 终止器必须先检查 `poll()`；已退出进程不再发信号。系统调用抛出 `OSError`、`ProcessLookupError` 时记录安全分类，不把路径、环境或 argv 写入错误文本。
- 终止超时不阻塞 Job 关闭：返回包含 `timed_out`、`root_kill_attempted`、`root_still_running` 的内部报告；上层由 Job 决定失败/取消/关闭报告。不得依赖 `psutil` 或新增系统级依赖。
- 工厂和终止器均可注入，真实平台测试与纯单元测试使用同一端口。

### 2.3 测试

覆盖 Windows/POSIX 的参数设置、PID 查询、正常退出、进程不存在、权限/系统调用失败、终止器超时、根进程兜底、重复终止和已退出进程；在当前平台执行真实父子进程树终止测试，另一平台通过注入工厂/终止器验证分支。

## 3. 模块 3：SubprocessJob

### 3.1 生命周期契约

`SubprocessJob(Job)` 固定 `JobKind.SUBPROCESS`，启动后由自身的 daemon 监控线程等待进程结束；Registry 只负责 admission 和 Scope 关闭，不直接操作句柄。

- `start()`：先进入 `running`，启动失败立即以安全错误标记 `failed`，释放句柄；不得留下监控线程。
- 正常退出码 `0` -> `succeeded`；非零退出码 -> `failed`，`JobInfo.exit_code` 保留退出码。
- `cancel()`：通过 ProcessGroup 终止整个树；只有确认载体结束后才标记 `cancelled`。
- 超时：监控/通信超时先终止整个树，回收残余输出，再标记 `failed`（错误分类为安全的超时类型）；主动取消与超时在内部原因上区分，但不把命令行写入 `JobInfo.error`。
- `wait()` 只等待 Job 终态；`close()` 幂等，负责取消、等待监控线程并确保句柄回收。关闭截止时间到达时返回/抛出 `JobCloseTimeout` 或由 Scope 汇总为 `CloseReport.timed_out`，不能遗留根进程。

### 3.2 输出兼容边界

提供不可变 `SubprocessResult`（stdout、stderr、格式化文本、截断信息、退出码）供未来适配器读取；`JobInfo` 只保存状态、退出码、PID 和经过 `ErrorFormatter` 的错误。复用 `WorkspaceCommand` 当前的 UTF-8 替换、`stdout:`/`stderr:` 标签、20,000 字符总上限和截断标记算法，必要时抽取为无业务依赖的共享 helper，但本阶段不改 `WorkspaceCommand`。

### 3.3 测试

启动失败、正常/非零退出、stdout/stderr 截断、超时树终止、主动取消、通信异常、重复 `start/wait/cancel/close`、监控线程退出、句柄释放和错误不泄露环境/凭据。验证与 Registry 注册后终态会准确释放 lane slot。

## 4. 模块 3：ThreadJob

定义目标函数协议 `worker(cancel_event) -> object`（可提供兼容无参数包装器），内部使用 `threading.Event` 协作取消，线程保持 daemon 以保留当前安全边界。

- `start()` 创建唯一 worker；重复启动拒绝。
- 返回且未收到取消 -> `succeeded`；抛出异常 -> `failed`（只保存安全格式化错误）；收到取消后正常返回 -> `cancelled`。
- `cancel()` 只设置事件，不尝试强杀 Python 线程；多次调用幂等。
- `close(timeout)` 设置取消并等待；截止时间到达时 Job 保持 `running`，`CloseReport.timed_out`/诊断记录包含安全的 `JobCloseTimeout` 分类，线程继续作为 daemon 运行。线程最终退出后由唯一的 `finally` 路径标记终态并让 Registry 释放资源，避免把仍在运行的线程伪装为终态。
- 线程退出后的清理（事件、结果引用、listener）必须幂等；不持有 RuntimeState、Registry 锁或用户凭据。

测试覆盖协作取消、异常、关闭超时后最终退出、忽略取消的 daemon 线程诊断、线程启动失败、重复关闭及 Registry 资源释放。

## 5. 模块 3：ServiceJob

定义协议无关的 `ServiceDriver`：`start()`、`health_check()`、`close()`，可选 `rebuild()`；每个实例拥有独立 driver 句柄、关闭边界和计数器。MCP 不在本阶段实现，只验证驱动端口足以承载后续受控 transport。

建议的独立健康状态：`starting`、`healthy`、`degraded`、`rebuilding`、`stopped`；它不覆盖 Job 主状态（服务运行期间 Job 仍为 `running`，关闭后为 `cancelled`，初始化/重建耗尽为 `failed`）。

生命周期规则：

- 初始化必须有超时；失败进入 `failed` 并释放本实例资源。
- 健康检查连续失败达到阈值 -> `degraded`，按退避策略重建；恢复后回到 `healthy`。
- 重建次数耗尽 -> Job `failed`，保留安全诊断（失败次数/分类，不含协议载荷、环境和 owner）。
- `close()` 先停止健康监控，再关闭当前 driver，幂等且有独立超时；旧实例句柄不能被新实例复用。

健康变化通过独立的 `ServiceHealthListener`/driver 回调报告给事件桥；不能借用 `JobStateChange` 伪造 `running -> running` 的状态转换，也不能在 driver 线程直接触碰 Runtime。

测试启动失败、初始化超时、健康降级/恢复、连续失败、重建成功/耗尽、关闭超时、重复关闭和句柄隔离。

## 6. 模块 4：Registry/Scope 注入

### 6.1 所有权层级

固定层级为 `SYSTEM -> USER -> RUNNER -> RUN`，后续子 Agent/后台任务使用 `TASK` 子 Scope。`WebAppState` 持有共享 `JobRegistry` 的系统 Scope；本地 `build_application/build_runner` 默认创建独立 Registry，并明确 `owns_registry`。Runner 只拥有并关闭自己的 Runner Scope，不得关闭共享系统 Registry。

Runner/Application 构造参数应接受可选 Registry/Scope，而不是让业务模块导入全局单例。创建顺序记录在 composition root：先 Registry/Scope，再 Runner，再 Application；任何中途失败按反向顺序关闭已经创建的 Scope/资源。

### 6.2 Runtime 重绑定

`RuntimeServices` 新增非序列化字段：当前 `JobScope`、Job 事件队列/桥和可选线程安全展示 sink。`AgentRunner.bind/resume` 重新创建或绑定 Run Scope，仅更新服务引用，不修改 `RuntimeState`、SQLite、JSONL 或同步快照。Scope/Registry/线程/句柄不得进入 dataclass 序列化、模型上下文或 checkpoint。

每次 `new_runtime` 为当前 run 创建临时 Run Scope；Run 正常结束、失败、取消或恢复失败均在同一清理入口关闭。所有注册路径沿 Scope API 执行，继续由现有 Registry 施加用户/Runner lane 配额和跨用户访问边界。

## 7. Runner/Application/WebAppState 关闭顺序

实现一个局部的“尝试全部关闭、汇总首个失败”策略，保持现有资源去重和幂等：

1. `AgentRunner.close()`：关闭 Runner Scope（停止后代 Job） -> 等待/记录关闭报告 -> 按逆序关闭尚未迁移的 legacy resources。一个资源失败不得跳过其他资源。
2. `AgentApplication.close()`：保留当前 sync 关闭兼容；先让 Runner 停止其 Job Scope，再关闭 sync/legacy 资源，收集所有失败后再报告。
3. `WebAppState.close()`：先关闭系统 Job Scope（停止所有用户/Runner/Run 后代 Job），再按现有顺序关闭 SnapshotManager、项目/数据库、认证、mailer、cloud；保留对象去重和多次 close 幂等。

验证 Runner 之间隔离、Runner 关闭不影响共享 Registry 中其他 Runner、Web 关闭能停止全部后代、构建失败/关闭失败仍清理其余资源，并兼容已有 ownership/shutdown 测试。

## 8. Job 事件桥与跨线程消费

### 8.1 事件模型

在 `RuntimeEventKind` 增加 `job_queued`、`job_started`、`job_succeeded`、`job_failed`、`job_cancelled`、`job_service_degraded`（名称稳定、非 checkpoint）。由于现有 `JobStateChange` 只覆盖状态变化，`job_queued` 由 Registry 的注册观察钩子（或等价的 `JobLifecycleListener.on_job_queued`）发出；lane/kind 等调度元数据从 `ScopedJobInfo` 读取，不能从线程回调自行猜测。Job state listener 只构造安全的领域事件，不直接调用 `RunEventPublisher` 或修改 `RuntimeState`。

事件数据最小集合：`job_id`、`job_kind`、`lane`、`state`、`session_id`、`run_id`（可用时）。禁止命令行、环境、原始异常、owner 内部标识、进程句柄和完整服务载荷；错误通过现有 redaction/ErrorFormatter 管线处理。

### 8.2 有界队列和 sink

提供线程安全、有界 `JobEventQueue`：发布使用非阻塞 `put_nowait`，满时丢弃展示/审计副本并计数；不得阻塞 Job 的取消或关闭。Runtime 所属线程在模型边界、工具边界和 Run 结束前显式 `drain()`，再交给当前 `RunEventPublisher`；前端使用独立线程安全 sink，不能从 worker 线程直接改 publisher/runtime state。

队列关闭后，新事件安全丢弃；Job Registry 状态仍是权威来源。处理“Job 已完成而 Runtime 正在关闭”的竞态：关闭流程先停止接收/标记队列，再关闭 Scope；drain 允许返回已入队事件但不重新打开 Runtime。

### 8.3 持久化边界

Job 事件不加入 `CHECKPOINT_EVENT_KINDS`，不触发 Runtime checkpoint，不进入模型请求上下文；允许通过现有 publisher/redaction 进入前端流和审计副本。测试应证明 JSONL/运行时持久化线程安全且 schema 兼容，事件丢失只影响副本不影响 Registry 状态。

## 10. 验收门槛与后续迁移条件

只有在以下条件全部满足后才开始业务迁移模块：

- 三类载体共享 `Job` 状态/监听/关闭语义，ProcessGroup 是唯一的裸 `Popen` 边界。
- 进程树终止、线程协作取消、服务降级/重建和关闭超时均有可重复测试。
- Registry/Scope 层级与用户配额隔离成立，Runner/Application/WebAppState 关闭顺序和幂等性成立。
- 跨线程事件有界、非阻塞、可丢副本，且不会进入 checkpoint 或模型上下文。
- 完整 pytest、Ruff 检查和格式检查通过，Windows 真实进程树测试通过。

之后再分别规划 WorkspaceCommand、受控 MCP transport、Web chat worker、Subagent、SyncCoordinator 和 SnapshotManager 的适配；每次迁移只接入一个业务载体并保留对应兼容测试。
